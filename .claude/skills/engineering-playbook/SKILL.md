## 0. กฎเหล็กของเจ้าของงาน (ห้ามข้าม)

> **"ตรวจสอบความถูกต้อง logic เพิ่มรายละเอียดการแก้ไข และต้องทดสอบแบบเต็มระบบทุกครั้ง จนกว่าจะเขียวครบทุกเงื่อนไขทุกการทดสอบ แล้วค่อย CI และเปิด PR"**
> **"ตรวจเต็มระบบผ่านแล้ว commit, CI แล้วเปิด PR"**

ลำดับบังคับ:

```
ตรวจ logic → บันทึกรายละเอียดการแก้ → full check เขียวครบ → commit → push/CI เขียว → เปิด PR
```

- ห้าม commit, push หรือเปิด PR ในขณะที่มีการทดสอบใดยังแดงอยู่ ไม่ว่าเทสนั้นจะ "ไม่เกี่ยว" หรือ "flaky" ก็ตาม
- คำว่า "เขียว" ต้องมีหลักฐานจากการรันจริงในรอบนี้ ห้ามอ้างผลจากรอบก่อนหรือคาดเดาเอา
- เมื่อ CI แดงหลัง push ต้องหาสาเหตุ แก้ แล้วรัน full check ใหม่ทั้งหมดก่อน push รอบต่อไป

## 1. Protocol การแก้/refactor

### 1.1 กฎ 8 ข้อ
| # | กฎ | ความหมายในทางปฏิบัติ |
|---|----|------------------------|
| 1 | ทำเป็น phase เล็ก | phase หนึ่งแก้เรื่องเดียว ต้อง review และ revert ได้ทีละ phase |
| 2 | Baseline ก่อนแก้ | รัน full check บนโค้ดเดิมก่อนแก้ จดผลไว้ จะได้รู้ว่าอะไรแดงอยู่แล้วและอะไรเราทำพัง |
| 3 | ไม่ทดสอบแค่ happy path | ต้องครอบคลุม input ผิด, ขอบเขตค่า, สิทธิ์, ทำซ้ำ, ทำพร้อมกัน, ระบบภายนอกล้ม, ทุก combination ของ flag/config |
| 4 | ห้ามอ้างผลที่ไม่ได้ทดสอบ | รายงานเฉพาะสิ่งที่รันแล้วเห็นผลจริง อะไรที่ยังไม่ได้ทดสอบให้บอกตรง ๆ ว่ายังไม่ได้ทดสอบ |
| 5 | ล้มแล้วหยุด | phase ไหนไม่ผ่าน ห้ามไป phase ถัดไป ให้หาต้นเหตุก่อน |
| 6 | รักษา API contract | ห้ามเปลี่ยน path, field, status code หรือ error code ที่ client ใช้อยู่ ถ้าจำเป็นต้องเปลี่ยน ให้บันทึกลงเอกสารสำหรับทีม FE |
| 7 | ไม่แตะโค้ดที่ไม่เกี่ยว | เจอปัญหาอื่นระหว่างทางให้จดลง OPEN-ITEMS ห้ามแก้แถมไปด้วย |
| 8 | กฎเหล็ก | ตามหมวด 0 |

### 1.2 Phase gate (ทุก phase ต้องผ่านทุกข้อ)
- [ ] เทสใหม่ **ล้มบนโค้ดเดิม** (control run: stash `src/` → รันเทสใหม่ → ต้องแดง → คืน src) เพื่อพิสูจน์ว่าเทสจับบั๊กได้จริง
- [ ] เทสใหม่ผ่านบนโค้ดใหม่
- [ ] full check เขียวครบ ได้แก่ typecheck, lint, unit, DB/integration, contract/parity และ boot ได้ทุก config
- [ ] อ่าน diff ตัวเองอีกรอบแบบหาเรื่อง ตั้งคำถามว่า CI หรือ reviewer จะปฏิเสธเพราะอะไร
- [ ] บันทึกครบตามหมวด 3

### 1.3 แก้บั๊ก = มีเทสที่ล้มก่อนเสมอ
1. เขียนเทสจำลองบั๊กแล้วรันให้เห็นว่าแดง
2. แก้โค้ดให้น้อยที่สุดเท่าที่จำเป็น
3. รันจนเขียว แล้วทำ control run ยืนยัน

## 2. วินัยการทดสอบ

- **"Flake ไม่ใช่ root cause"** เทสที่แดงเป็นบางครั้งคือบั๊กจนกว่าจะพิสูจน์ได้ว่าไม่ใช่
  - ตัวอย่างจริง: เทสแดงเป็นครั้งคราวเพราะ ID generator ชนกันข้าม process เมื่อรัน jest แบบ parallel วิธีแก้คือรัน DB tests แบบ `--runInBand` และบันทึกต้นเหตุไว้
- **Synthetic data ต้องไม่ชนกัน** แต่ละไฟล์เทสใช้ช่วง ID และ login ของตัวเอง และจดช่วงที่ใช้ไว้ที่หัวไฟล์
- **Snapshot**: ก่อนรัน `-u` ทุกครั้งต้องดู diff และอธิบายได้ว่าแต่ละบรรทัดเปลี่ยนเพราะอะไร ห้ามอัปเดตแบบไม่ดู
- **ระบบภายนอก** (payment, trading server, email/SMS) ให้ใช้ fake แบบ stateful ที่จำยอดและสถานะได้ และจำลองการล้มได้ทุกจุด ห้ามเรียก service จริงในเทส
- **ทดสอบทุก config/brand/flag combination** เช่น feature ปิดต้องได้ 404 และ boot ได้ทุก config
- **Concurrency**: ยิงคำขอซ้ำและพร้อมกันเพื่อตรวจ double-spend, duplicate ref และ deadlock
- **Invariant test**: หลังทุกเคส ผลรวมเงินต้องเท่าเดิม และ ledger ต้องตรงกับ balance
- **เมื่อสภาพแวดล้อมพัง** (เช่น DB ดับหลัง restart) ให้แก้ environment แล้วรันใหม่ทั้งชุด ห้ามข้ามเทส
- **ห้าม skip, disable หรือ quarantine เทส** เพื่อให้ผ่าน

## 3. วินัยการบันทึก (ทุกการแก้ต้องตามรอยได้)

| เอกสาร | บันทึกอะไร |
|--------|-----------|
| `FIX-LOG.md` | รหัสปัญหา (เช่น `MONEY-01`), อาการ, ต้นเหตุ, ไฟล์:บรรทัดเดิม, วิธีแก้, เทสที่พิสูจน์ และจุดที่ต้อง port ไปยัง repo พี่น้อง |
| `CHANGELOG.md` | สรุปราย phase หรือราย PR |
| `OPEN-ITEMS.md` | งานค้าง, คำถามรอตัดสินใจ, และสิ่งที่เจอแต่ไม่ได้แก้ แต่ละเรื่องมีรหัส สถานะ และ owner |
| `API-CHANGES-FOR-FE.md` | ทุกอย่างที่ client เห็นว่าเปลี่ยน เช่น error code ใหม่, validation ใหม่, field ใหม่ พร้อมตัวอย่าง request/response |
| เอกสารแยกตามเรื่อง | เรื่องที่ซับซ้อน (เช่น กฎธุรกรรมของสกุลเงินพิเศษ) ให้แยกไฟล์ และใส่ลิงก์ใน README index |

**บันทึกการตัดสินใจ** ต้องมีว่าใครตัดสิน เมื่อไหร่ และเหตุผลอะไร โดยแยกให้ชัดว่าข้อไหน "เจ้าของงานยืนยันแล้ว" และข้อไหน "ผู้พัฒนาเลือกเอง รอยืนยัน"

**Commit**
- แยก commit ตามชนิดงาน คือ fix, refactor, test และ docs
- ใช้ prefix เช่น `fix:`, `feat:`, `refactor:`, `test:`, `docs:`, `chore:`
- ข้อความ commit อธิบายว่า "ทำไม" ไม่ใช่แค่บอกว่า "ทำอะไร"

## 4. การตัดสินใจเชิงธุรกิจ: ถามเจ้าของ ไม่ตัดสินเงียบ ๆ

- กฎธุรกิจ เช่น ทศนิยม, ขั้นต่ำ, การคืนเงิน หรือสิทธิ์ ไม่ใช่สิ่งที่ dev ตัดสินเอง
- วิธีถาม:
  - แสดงหลักฐาน ได้แก่ โค้ดปัจจุบันทำอะไร, ข้อมูลจริงเป็นอย่างไร, เอกสารเดิมว่าอย่างไร
  - ให้ตัวเลือกพร้อมผลกระทบ และแนะนำ 1 ทาง
  - ทำตารางสรุปรายเคสให้เจ้าของตอบ "ตรง/ไม่ตรง" ได้ทีละแถว
- ถ้าเจ้าของงงหรือสื่อสารไม่ตรงกัน ให้หยุดแล้วอธิบายใหม่ด้วยตัวอย่างตัวเลขจริง ห้ามเดินหน้าต่อทั้งที่ยังไม่เคลียร์
- คำตอบจากการทดลองบน production จริงของเจ้าของ (เช่น "ลองแล้ว ถอนได้ 2 ตำแหน่ง") มีน้ำหนักกว่าการตีความจากโค้ด
- เมื่อได้ข้อสรุปแล้ว ให้บันทึกลงเอกสารทันที (หมวด 3)

## 5. ขอบเขตงานและความลับ (ห้ามละเมิด)

- **ทำเฉพาะ scope ของตัวเอง** เช่น ทำแค่ backend API ห้ามแตะ frontend หรือ backoffice ของทีมอื่น
  - ถ้าต้องแก้ฝั่งอื่น ให้เขียน handover ลง OPEN-ITEMS แทน
  - ถ้าเผลอแตะไปแล้ว ให้ revert ออกให้หมด
- **โค้ดเป็นความลับ** ห้ามเผยแพร่ ห้าม publish เป็นหน้าเว็บหรือลิงก์สาธารณะ และห้ามแปะลงบริการภายนอก
- **Secrets**: ห้าม print, log หรือ commit credential เด็ดขาด
  - `.env.example` และไฟล์ config ใน repo ต้องไม่มีค่าจริง
- **ข้อมูล staging/production** (export, dump):
  - ใช้วิเคราะห์ได้ แต่ห้าม commit และห้ามคัดลอกลงเอกสาร
  - เก็บไว้ใน scratchpad หรือ temp นอก repo เท่านั้น
  - อ่านเฉพาะคอลัมน์ที่จำเป็น (PII)
  - เอกสารให้อ้างอิงเป็นสถิติหรือรูปแบบ ไม่ใส่ข้อมูลรายบุคคล
- **Git**:
  - push เฉพาะ branch ที่ได้รับมอบหมาย
  - ห้าม force-push หรือ rewrite history บน branch ของคนอื่น
  - งานที่ PR merge ไปแล้ว ถ้ามีงานต่อให้เริ่ม branch ใหม่จาก main
- **Repo ที่สั่งพักไว้** (เช่น repo พี่น้องที่ต้อง port) ห้ามแตะจนกว่าจะสั่ง แต่ต้องจดจุดที่ต้อง port ไว้ใน FIX-LOG

## 6. หลักการ Money path (ระบบที่เกี่ยวกับเงิน)

1. **แปลงจำนวนเงินเป็น number ที่จุดเข้า** body อาจส่งมาเป็น string แล้ว `balance + "5"` จะกลายเป็นการต่อ string
   - รับเฉพาะ finite number หรือ string ทศนิยมธรรมดา ปฏิเสธ `1e3`, `""`, `Infinity` และ object
2. **ไม่เชื่อค่าจาก client** เรื่องจำนวน, rate, สกุลเงิน และค่าธรรมเนียม สกุลเงินต้องมาจาก wallet ใน DB ไม่ใช่จาก body
3. **กฎทศนิยมชัดเจนต่อสกุลและต่อประเภทรายการ** ต้องมีขั้นต่ำ ≥ หน่วยเล็กสุด และจำนวนทศนิยมจำกัด
   - เลือกจำนวนทศนิยมให้การแปลงสกุลเงินลง column DECIMAL ได้ "พอดี" จะได้ไม่มีเงินเกิดหรือหายจากการปัดเศษ
4. **ห้ามปัดเงียบ** ถ้าค่าผิดกฎให้ตอบ 400 พร้อม error code ห้ามปัดแล้วทำต่อ
5. **ทำรายการกับระบบภายนอกก่อน แล้วชดเชยถ้าส่วนหลังล้ม** (compensation หรือ reversal) และถ้าการชดเชยเองก็ล้ม ต้องยิง alert ให้ support ทันที
6. **Idempotency**:
   - reference ต้องผูกกับเจ้าของ
   - ref ซ้ำของคนเดิมให้คืนผลเดิม
   - ref ซ้ำของคนอื่นให้ตอบ 409 ห้ามคืนข้อมูลของคนอื่น
7. **Lock และ transaction**: lock row เรียงลำดับเดิมเสมอเพื่อกัน deadlock และใช้ conditional update (`WHERE balance >= x`) เพื่อกัน double-spend
8. **Invariant ในเทส**: ทุกเคสต้องตรวจผลรวมเงินก่อนและหลัง ทั้ง ledger และ balance ฝั่งภายนอก
9. **ยึดข้อมูลจริงเป็นหลัก**: วิเคราะห์ export จริงเพื่อหาเคสที่เคยพัง แล้วแปลงเป็นเทส matrix ให้ครบทุกการทำรายการ × ทุกสกุล × ทุกเคสผิดพลาด
10. **เรื่องที่ยังไม่ได้ทำ** เช่น reconciliation หรือการรองรับหลาย instance ให้บันทึกเป็น open item พร้อมเงื่อนไขว่าเมื่อไหร่ต้องทำ

## 7. Logging และ Alert

- ใช้ structured logger (JSON) เท่านั้น ห้ามใช้ `console.*`
- ตั้งชื่อ event เป็น `domain.action_result` เช่น `mt5.reversal_failed`
- แยกหมวด alert ว่าเรื่องไหนต้องแจ้ง support ทันที
- ห้าม log secret, token, OTP, รหัสผ่าน หรือ PII เต็มรูปแบบ

## 8. Code conventions ทั่วไป

- **แบ่ง layer** ดังนี้ route → controller (รับ/ตอบ HTTP) → service (logic) → repository/DB และห้ามข้าม layer
- **Error**: ใช้ error class มาตรฐาน (Validation, NotFound, Conflict, …) และส่ง error code ที่ client ใช้ได้เสมอ
- **ชื่อตารางและคอลัมน์**: ใช้ constant ห้าม hardcode string ซ้ำ ๆ
- **Env**: ค่าที่ไม่บังคับต้องมี default ส่วนค่าที่บังคับให้ fail-fast ตอน boot
- **i18n**: ข้อความถึงผู้ใช้ใช้ key ไม่ hardcode ภาษา
- **Multi-tenant/whitelabel**:
  - ห้ามมี brand literal ใน src และห้ามมี `if (brand === 'x')`
  - ใช้ config หรือ feature flag แทน
  - field ต้องมีครบทุก brand
  - feature ที่ปิดอยู่ต้องตอบ 404
- **DB schema เป็นของ DBA**: ห้ามแก้ schema เอง ถ้าจำเป็นให้เสนอ migration ผ่านช่องทางที่กำหนด
- **แก้ให้น้อยที่สุด** และเขียนให้กลมกลืนกับโค้ดรอบข้าง ทั้งสไตล์ ความหนาแน่นของ comment และการตั้งชื่อ

## 9. PR และ CI

- **PR checklist**:
  - full check เขียว (แนบผล)
  - มีเทสที่ล้มบนโค้ดเดิม
  - อัปเดตเอกสารครบ
  - ระบุผลกระทบต่อ FE
  - ไม่มี secret หรือข้อมูลจริงหลุดเข้าไป
- **หลังเปิด PR**: เฝ้า CI และ review
  - CI แดงให้แก้ที่ต้นเหตุ ห้ามกด re-run ซ้ำ ๆ
  - ห้ามดัน empty commit เพื่อกระตุ้น CI
- ทุก review comment ต้องได้คำตอบ จะแก้หรือไม่แก้ก็ต้องบอกเหตุผล
- **Merge แล้วจบ**: งานต่อเนื่องให้เปิด PR ใหม่จาก main ล่าสุด

## 10. การสื่อสาร
